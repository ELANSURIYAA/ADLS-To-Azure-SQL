1. Data Expectations

1.1 Completeness
- All ~400,000 active SCAN member records must be migrated from EDH to Microsoft Dataverse CRM with zero data loss.
- Each member Contact record must be fully populated with mandatory demographic fields: First Name, Last Name, Member ID, Date of Birth, phone, and email.
- All related entities (Enrollment, PCP History, Communication Preferences, Address) must be linked to the correct Contact.

1.2 Accuracy
- All migrated data must match the source EDH data with no discrepancies, as verified by reconciliation and random sample validation.
- All verification test scenarios must pass, confirming data integrity.

1.3 Format
- Phone numbers must conform to E.164 format (e.g., +1XXXXXXXXXX).
- Email addresses must conform to RFC 5322 standard (e.g., user@domain.com).
- Date fields (e.g., Date of Birth) must use ISO 8601 format (YYYY-MM-DD).
- Address fields must comply with USPS standards (Line1, City, State, Zip).

1.4 Consistency
- No duplicate Member ID records are allowed post-migration; pre-migration deduplication is required.
- All foreign key relationships (e.g., Enrollment, PCP History, Communication Preferences, Address to Contact) must be consistently maintained.
- PHI fields must be consistently secured and accessible only to authorized roles.

2. Constraints

2.1 Mandatory Fields
- Contact: First Name, Last Name, Member ID, Date of Birth, Main Phone, Email, EDHMemberId (Record ID).
- Enrollment: EDHEnrollmentId (Record ID), PlanName, PlanStatus, PlanEndDate, PlanEffectDate, PlanID, EDHMemberID (FK to Contact).
- PCPHistory: EDHMemberServiceRequestId (Record ID), PCPName, PCPID, PMGPhoneNumber, PCPEffectiveDate, Specialty, PCPEffectiveEndDate, EDHMemberId (FK to Contact).
- CommunicationPreference: CommunicationCategory, DeliveryMethod/Name, Preferred, TextOptIn, EDHMemberID (FK to Contact), CommunicationType, CommunicationSubCategoryCode, EDHMemberCommunicationPreferencesId (Record ID).
- MemberAddress: EDHMemberId (FK to Contact), Line1, City, State, PostalCode, PeriodStart, PeriodEnd, EDHMemberAddressId (Record ID).

2.2 Uniqueness
- Member ID (new_memberid) must be unique across all Contact records.
- EDHMemberId, EDHEnrollmentId, EDHMemberServiceRequestId, EDHMemberCommunicationPreferencesId, and EDHMemberAddressId must be unique within their respective entities.

2.3 Data Type Limitations
- Member ID: Text, max 15 characters.
- Date fields: Date or DateTime, ISO 8601 format.
- Phone: Text, E.164 format.
- Email: Text, RFC 5322 format.
- Boolean fields: 1 or 0.
- Foreign keys: Must reference valid Contact records.

2.4 Dependencies & Referential Integrity
- Enrollment, PCP History, Communication Preferences, and Address records must reference a valid Contact (FK).
- No orphaned child records are allowed.

2.5 Security & Compliance
- PHI fields must be secured per HIPAA requirements.
- Role-based access enforced; only authorized Advocate roles can access PHI fields.

2.6 Audit & Performance
- Migration audit logs must be retained for 18 months, capturing record counts, success/failure status, and per-record error details.
- Post-migration search response time must be under 2 seconds across all 400,000 records.
- Migration must complete within the agreed SLA batch window (e.g., 8 hours).

3. Business Rules

3.1 Migration & Data Processing
- All ~400,000 active SCAN member records must be migrated in a single batch process without data loss.
- Pre-migration deduplication must be performed to ensure no duplicate Member IDs.
- All field mappings must be implemented as per the specification.
- Static fields (e.g., Source System = 'EDH') must be populated as specified.

3.2 Data Transformation
- Phone numbers must be transformed to E.164 format if not already compliant.
- Email addresses must be validated and transformed to RFC 5322 compliance.
- Date fields must be transformed to ISO 8601 format.
- Address fields must be validated against USPS standards.

3.3 Security & Access
- PHI fields must be encrypted or otherwise secured in the CRM.
- Only authorized Advocate roles can access PHI fields; unauthorized roles must be blocked.

3.4 Audit & Logging
- Migration process must generate audit logs capturing record counts, success/failure status, and error details for each record.
- Audit logs must be retained for 18 months for compliance and traceability.

3.5 Performance & SLA
- Migration must complete within the agreed SLA batch window (e.g., 8 hours).
- Post-migration search queries must return results in under 2 seconds for all 400,000 records.

3.6 Verification & Validation
- All verification test scenarios (search by Member ID, Last Name + DOB, random sample validation, duplicate check, PHI access control) must pass before migration sign-off.
- All field mappings must be validated against the specification.
- Zero data loss must be confirmed by reconciliation report.
- HIPAA compliance and PHI access controls must be tested and verified.

3.7 Definition of Done
- All requirements above must be met and signed off by Member Services and IT leads before migration is considered complete.
